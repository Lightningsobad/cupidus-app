## User Story
As a paired user viewing our relationship timeline, I want the countdown,
progress ring, and photo-entry list to match the locked design source
exactly, so our shared history feels polished and on-brand.

## In Scope
1. Re-audit the current Love Timeline screen against
   `cupid-app-design-system` for the enabled dark theme + `vi` locale
   configuration: relationship countdown display, progress-ring component
   styling, photo/milestone entry list layout (including `<image-slot>`
   placeholder treatment), spacing, color/design-token usage, and
   typography.
2. Correct every deviation found directly in the app code so the rendered
   screen matches the design source exactly — this is a fix, not an audit
   report.

## Out of Scope
- Any new feature, new screen state, or new interaction not already present
  in the locked design source.
- Light theme / `en` locale user-facing visual QA (OQ5 — infra-only, not
  enabled for users yet); token-level fixes should stay correct for all 4
  combinations since tokens are shared, but no dedicated light/`en` visual
  pass is required.

## Acceptance Criteria
1. Given the Love Timeline screen rendered in the enabled dark theme + `vi`
   locale, when compared against `cupid-app-design-system`'s corresponding
   screen, then layout, spacing, color/token usage, and typography match
   exactly with no visible deviation.
2. Given any deviation was found during this story's audit, when the story
   is delivered, then the deviation is corrected in the rendered app (not
   merely documented) and re-verified against the design source.
3. Given the countdown and progress-ring components, when rendered, then
   their visual treatment (fill state, numerals, ring styling) matches the
   design source exactly.
4. Given a photo/milestone entry using an `<image-slot>` placeholder in the
   design source, when rendered, then the placeholder treatment matches
   exactly; this story does not implement real photo-upload behavior.
5. Given the screen is reached through its existing normal navigation path,
   when a user arrives at it, then no new entry point is required — this
   story does not change how the screen is reached.
